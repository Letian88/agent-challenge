# Design

## Context

参赛契约见 proposal.md 与 `specs/competition-a-dpa-deploy/spec.md`。实际题包定义固定模型 DPA4C-Nano-OMat24-v20260819、单张 PPU810E 96GB、CuNi/Si/MgO 三类材料和九个公开场景；组织方还可能在给定原子数、温压及成分范围内更换输入。当前题包未通过自身完整性检查，冻结环境又同时记录 `release_candidate_ready: true` 与 `release_ready: false`，因此本设计先处理证据与门禁，不把沙箱启动视为可执行步骤。

## Goals / Non-Goals

**Goals:**

- 建立“题包完整 → 资源版本一致 → 账号与算力可用 → 自测 → 优化 → 完整九题 → 打包提交”的可验证顺序。
- 隔离基线、候选和未压缩正确性参考，确保性能改动不污染判定基准。
- 每轮改动同时保留正确性、性能和可复现构建证据。

**Non-Goals:**

- 本变更不启动 PPU 沙箱、不下载大资产、不修改候选实现、不构建镜像或提交比赛答案。
- 不根据通用平台元数据臆测正式成绩；不补写题包没有给出的截止日期。

## Decisions

- **先过题包完整性门禁**：只有同时找到 `instruction.md` 和 `asset/tools/arena.py` 的唯一根目录后才允许启动收费资源。替代方案“先开沙箱再补文件”违反题面明示流程，因此否决。
- **资源版本必须由组织方消歧**：配置、challenge 元数据和落盘目录均指 v5，但下载说明示例写 v4。不得自行选择或混用版本；澄清结果要记录在团队事实源中。
- **三条执行链隔离**：基线保持不动，候选只通过 `asset/starter/engine.json` 定位，正确性由未压缩参考独立重算，避免以候选自证正确。
- **正确性先于速度**：每次改动先跑数值回归，再跑单场景配对，稳定后才跑同一次完整九题评测；不同改动的历史最好成绩不得拼接。
- **复现材料与实现同步**：手工修改、编译选项、精度策略和导出步骤必须同步进最终 Dockerfile、脚本、补丁和 `optimization.md`；沙箱状态本身不算交付。

## Risks / Trade-offs

- [缺少 `instruction.md`] → 保持阻塞并向组织方提交下载路径、challenge ID 与文件清单，不启动收费沙箱。
- [v4/v5 资源错配] → 等待书面确认后固定版本及哈希；确认前不执行大资产下载。
- [冻结环境未标记正式就绪] → 要求组织方解释或补发配置，不能用 `release_candidate_ready` 推断可执行状态。
- [平台通用 0–100 元数据与九题几何平均冲突] → 以详细题面作为工作口径，同时在正式提交前让组织方确认服务端验收入口。
- [PPU 数学路径带来精度偏差] → 每个优化同时验证能量、力、应力、NVE 漂移与 NVT/NPT 统计，不以单一速度指标放行。
- [公开场景过拟合] → 候选不得硬编码结构、原子数或工况，并用题面声明的输入范围设计泛化检查。
- [比赛截止时间缺失] → 只记录“每天最多 5 次提交”和运行超时等已知限制，截止日以组织方后续公告为准。
